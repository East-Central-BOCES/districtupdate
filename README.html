ECBOCES District Update setup

# ECBOCES District Update

A Moodle **5.1.1** local plugin for annual district staff reviews and administrator-approved Active Directory changes. Component: `local_districtupdate`. **Pilot build, version 0.1.9.** AD writes and automatic annual invitations default to off.

## What districts see

A signed-in, assigned reviewer sees only their district’s roster. Every account starts as **Still Employed**. Reviewers change exceptions to **No longer employed with an ECBOCES district** or **Moved to another ECBOCES district**. Choosing a transfer reveals a required dropdown of district names. Notes are optional. Multiple assigned people share the same roster, with attribution for changed responses and the final submitter. A stale save is rejected rather than overwriting another person’s work. Submitting freezes the roster; saving progress does not submit it or execute AD changes. District reviewer access expires exactly 30 days after submission: the review is hidden from their dashboard and direct links are denied. Administrators retain access. Expiration applies to each review, including existing submissions, without deleting roster data or removing the district assignment used for future annual cycles. An administrator can reopen an unprocessed review to restore reviewer access; resubmission starts a new 30-day window.

## Approved actions

| AD change | Still employed | No longer employed | Moved to another district |
|---|---|---|---|
| ECBOCES_Members | No change | Remove | Retain existing membership |
| Zoom | No change | Remove | Remove |
| Basic | No change | Add | Add |
| Office (`physicalDeliveryOfficeName`) | No change | `No Access` | `No Access` |
| Company (`company`) | No change | No change | Exact selected district name |

Company is changed in AD. Your existing LDAP mapping and sync carries it into Moodle Institution. The plugin does not delete, disable or suspend AD accounts and does not change Moodle authentication configuration.

## Install

1. Use a Moodle 5.1.1 staging site for the pilot. Install `local_districtupdate-0.1.9.zip` through **Site administration → Plugins → Install plugins**, or place the plugin files in your Moodle **`public/local/districtupdate/`** folder. The folder must be `districtupdate` and contain `version.php` directly. Moodle 5.1 moved web code under `public`; use your actual Moodle web-code root.
2. Complete the upgrade through **Site administration → Notifications**. No core file edits are needed.
3. Open **Site administration → Plugins → Local plugins → District staff review** for settings, and **Manage district staff reviews** for districts and annual rosters. Direct dashboard: `/local/districtupdate/index.php`; management: `/local/districtupdate/manage.php`.
4. Keep **Enable approved AD writes** and **Automatically start annual reviews** off while setting up and checking the roster.

The installer creates six plugin tables. The ZIP contains one `districtupdate/` directory. The repository root is the plugin source; do not install the parent folder name `districtupdate-main` as the Moodle plugin directory.

## Updating from 0.1.0

Version 0.1.1 removes empty-string defaults from all seven required CHAR fields in the installation schema. Moodle XMLDB already normalizes these defaults when creating tables, so this correction does not change existing data or require a database migration. Replace the existing plugin files with this version and visit **Site administration → Notifications** to finish installation or apply the version update. Do not uninstall the plugin to apply this fix.

## Configure districts and reviewers

In **Manage district staff reviews**, add every district before creating a year’s roster. Add **one district at a time**, then choose **Save district and add another**. The district-name box holds one name; Enter moves to the email-domain box without saving. The larger boxes below accept multiple lines using Enter:

- **Exact district name:** the name to write into AD Company for transfers (maximum 64 characters).
- **Email domains:** one domain per line, without `@`.
- **Institution aliases:** other existing Company/Institution values identifying this district. The district name itself already matches. Matching ignores case and surrounding whitespace. Shared domains should be left off both district mappings so Institution can distinguish them.
- **Assigned Moodle usernames:** one or more active, non-guest Moodle usernames, one per line. These people can use the same review link, but must each log into their own assigned account. Forwarding the URL does not grant another person access. Assignment changes take effect immediately for future requests.

The roster includes **non-deleted, non-suspended Moodle users whose authentication method is selected in Roster authentication methods**, excluding site administrators and configured excluded usernames. The default selection is `ldap`. Select every applicable LDAP method, including plugins with other names; multiple selections are supported. Installed plugins and authentication names currently found on Moodle accounts are offered. An empty selection includes no users. This setting does not change account authentication or login behavior. All selected methods use the existing one central ECBOCES AD connection for approved changes, with the same username/email identity checks. Changing the selection invalidates existing AD previews; refresh draft rosters afterward to apply it. It does not query AD enabled status when generating the roster. Confirm that your LDAP synchronization correctly reflects which accounts belong in the annual review. Add shared/service accounts to **Excluded usernames** before generating a roster.

Matching uses email domain, Institution, and the additional **District** user profile field. The District value matches configured district names or the same aliases used for Institution, ignoring case and surrounding whitespace. If any recognized sources disagree, or a source matches multiple districts, the account stays unmatched for administrator assignment. Blank or unrecognized profile values leave the existing email/Institution matching available. The **District custom profile field** setting defaults to `district`: it resolves a case-insensitive shortname first, then a unique display name. Set the actual shortname if different, or leave the setting blank to disable this source. If no field exists, matching continues with email and Institution. Use an administrator-maintained profile field. This reads the additional profile field for matching; it does not overwrite Institution or the custom profile field, and AD changes still follow the established Company rules. Conflicting or ambiguous evidence, and users with neither match, go to **Unmatched accounts** for administrator assignment. A shared or ambiguous domain is deliberately not guessed. Creating a roster takes a snapshot. Use **Refresh rosters from Moodle** under that year to update untouched draft entries after new users sync or district matching changes. Newly configured districts receive an open review during refresh. Each year can be created only once, but it can be refreshed repeatedly.

## Annual workflow

1. Enter review year and due date and choose **Create annual roster**.
2. Resolve unmatched accounts and inspect each district roster. No email is sent just by creating a roster manually.
3. Choose **Send invitations to all outstanding districts**, or send a district’s review link individually. All assigned reviewers receive the same district link. Notifications and delivery failures are logged.
4. Reviewers save progress and then choose **Submit completed review**. A completed review may leave every account as Still Employed, as requested. They are explicitly confirming the entire roster.
5. By default, site administrators receive an email whose body contains only a link to the protected approval page; staff names, email addresses, notes, submitter names and proposed actions stay inside Moodle. The subject identifies the district. The administration dashboard remains the authoritative source even if email delivery fails.
6. Under **Preview / process / audit**, changed accounts are checked by default. Uncheck exceptions or select an individual account, then choose **Preview selected accounts**.
7. With AD writes enabled, the preview checks live AD identity and state. Blocked accounts are identified and skipped. Choose **Confirm and process these accounts** to execute the approved subset. Preview mode shows proposed actions without an AD connection or an execute control.
8. Inspect results and the per-action audit. Reopening is allowed only before any processing attempt. Already completed accounts are not processed twice. A failed or interrupted account can be retried only through a fresh preview.

For very large batches, hosting gateway request limits may interrupt the browser response. Processing releases the Moodle session lock and requests unlimited PHP execution time, but host/proxy limits still apply. Inspect the dashboard and audit before retrying; per-review locking prevents overlapping execution. A background job queue is not implemented in this pilot.

## Invitation POST verification

Version 0.1.5 initializes the page context and metadata before POST actions, including invitations, reviewer submission and approval processing. `verification/moodle_invitation.php` exercises the actual management-page invitation POST using a synthetic reviewer and confirms delivery in local Mailpit. Its temporary database fixtures are rolled back. It refuses to run unless SMTP points to the local Mailpit catcher; it never resends invitations to configured district reviewers. Run with `php verification/moodle_invitation.php /path/to/moodle/config.php --test-site` only in the local test environment.

Version 0.1.9 adds custom District profile matching to initial rosters and draft refresh. After upgrading, use **Refresh rosters from Moodle** for existing drafts. Responses, manual assignments and submitted/processed rosters retain the existing preservation rules.

## Email message settings

Under **Site administration → Plugins → Local plugins → District staff review**, find **Email messages**. Edit the reviewer invitation/reminder subject and message, or the admin submission notification subject and message. Messages are plain text. Saving settings does not send email; future sends and reminders use the saved templates.

Supported placeholders: `{district}` (district name), `{year}` (review year), `{duedate}` (formatted due date), and `{reviewurl}` (district review link for invitations; protected approval link for admin notifications). If a message omits its link, the link is appended automatically. Blank fields fall back to the original defaults. Admin messages default to the link alone and never automatically include staff lists, employment decisions, notes, or submitter names. Subject lines are restricted to a single line. These settings are available only to site configuration administrators.

## Reviewer access and notification checks

Version 0.1.7 added per-review access expiration and link-only admin notification bodies; version 0.1.8 adds configurable plain-text email templates. `verification/moodle_security.php` checks recent and expired access using a real Moodle reviewer, dashboard visibility, retained data, administrator access, reopening, the actual email body received in local Mailpit, and editing templates through the real Moodle settings API with customized admin and reviewer emails captured locally. All database fixtures roll back. It refuses to run with any other SMTP destination. Run `php verification/moodle_security.php /path/to/moodle/config.php --test-site` only in the local test environment.

## Audit log retention

Audit entries are retained for **30 days** by default. The enabled daily task **Delete expired district-update audit entries** removes entries strictly older than the retention cutoff; entries exactly 30 days old remain until a subsequent run. Cleanup is scheduled for approximately 03:00 in the Moodle site timezone and depends on Moodle cron running. It runs independently of the annual-invitation automation setting. Adjust **Audit log retention** in plugin settings if needed.

Cleanup deletes only this plugin’s audit entries. Annual rosters, district responses, submitter attribution, manual district assignments and processing state remain intact. Existing manual assignments are migrated into durable roster state before cleanup is enabled, so they survive audit expiration. The audit time column is indexed for cleanup. Moodle’s own task execution logs use Moodle’s separate retention rules.

The management page displays up to 100 general audit entries and the approval page up to 200 per-review audit entries. Both show the retention period. Expiration removes individual action details and old snapshots stored in the audit history; the current roster and outcome status remain.

## Refresh an existing annual roster

Under the year’s heading in **Manage district staff reviews**, choose **Refresh rosters from Moodle**. A summary reports added users, updated profiles, district reassignments, removed inactive/excluded untouched entries, preserved responses and skipped locked reviews.

- New users are added with **Still Employed** prefilled; newly configured districts are included.
- Untouched entries get current Moodle name, username, email and Institution values and are rematched using current district rules. Conflicting/unmatched entries remain in the administrator queue.
- Untouched entries that are no longer eligible active users from the selected authentication methods in Moodle are removed from the draft, with their former snapshot kept in the administrator audit. AD accounts are not removed or changed.
- Recorded employment responses, notes, reviewer attribution and administrator district assignments are preserved, including their recorded identity snapshot.
- Submitted reviews are left unchanged. Reopen a submitted review before refreshing it, provided AD processing has not been attempted. Reviews with any attempted processing are never refreshed, and their users are not duplicated elsewhere in the same annual roster.
- An incoming user whose destination review is locked is skipped until that review can be reopened. Changed drafts invalidate previously opened forms so a stale save cannot overwrite the refreshed roster. An unchanged refresh does not invalidate the form.

Refresh uses the users **already synced into Moodle**. It does not start an LDAP synchronization, send invitations or execute AD changes. The existing invitation buttons remain separate.

## AD connection setup

The Moodle web server needs PHP’s LDAP extension, network access to the domain controller over LDAPS, and trust in the issuing certificate authority. **Certificate verification is required.** Use one `ldaps://hostname:636` URL without a trailing path.

Configure:

- LDAPS server URL.
- User search base DN, including relevant child OUs.
- A dedicated delegated service account bind DN.
- The full distinguished names of the **ECBOCES_Members**, **Zoom**, and **Basic** groups. Group names alone are not sufficient.
- The AD identity attribute that exactly matches Moodle usernames: `sAMAccountName` by default, or `userPrincipalName`.
- The bind password through `$CFG->forced_plugin_settings['local_districtupdate']['bindpassword']` in the real Moodle `config.php`, before it loads `lib/setup.php`. See `config.example.php`. Do not put real credentials into this repository.

Delegate read access for identity/group verification and write access only to **membership of the three named groups** and users’ **Company and Office attributes** in the relevant OUs. Do not use Domain Admin credentials. Existing Moodle LDAP credentials may be read-only; the plugin uses its own explicitly configured account.

Choose **Test LDAPS connection and group DNs** before enabling writes. This tests the bind and identifies the groups without changing accounts; it does not prove write permissions or account matching. Then enable writes only on the staging pilot and validate a small approved test batch.

At preview and again before processing, the plugin checks exact username and email matching, object GUID and current state. It refuses protected accounts and conflicting Company values. Object GUID is first pinned at the live preview, not at the annual snapshot; review reused usernames/email addresses manually. Inherited or primary group paths that prevent removing the requested membership are blocked before changes. This pilot assumes a single AD domain and same-domain groups.

AD changes span multiple directory entries and cannot be made into one atomic transaction. The plugin records the initial state and each attempted/successful/failed action. Earlier successful actions remain applied after a later failure. Retrying rechecks the current state and does not add duplicate memberships. Office and Company are replaced together in a single user-entry request for transfers. Post-change verification confirms the intended result before an account is marked complete. Existing AD/Moodle sync and any license provisioning must be tested end to end; an LDAP write alone does not prove the downstream effect.

## Annual scheduling and reminders

Moodle cron runs the task **Create annual district reviews and remind outstanding reviewers** daily. Moodle cron itself must already be working.

- **Automatically start annual reviews** is off by default. When enabled, this year’s roster is generated on or after the configured month/day, with a deadline based on **Days to complete review**, and invitations are sent automatically. Enabling it after the configured date starts this year’s cycle on the next task run.
- The default suggested start is August 1, with 30 days to complete; change these to your actual schedule before enabling automation.
- Reminder interval defaults to seven days; zero disables reminders. Reminders apply to invited, unsubmitted reviews for the current year, including manually invited reviews. Submitted districts stop receiving reminders.
- Dates follow the Moodle site timezone. Set it to **America/Denver** if that is your intended schedule.

## Access and data

Site administrators manage the plugin by default. A delegated role can be granted `local/districtupdate:manage` in system context; this is a sensitive permission that can approve directory changes. Ordinary reviewers receive access through district assignments, without a site administration role. The plugin includes Moodle Privacy API metadata, export, and local-data deletion support. Privacy deletion does not change AD.

Review forms contain three inputs per staff member. For large districts, configure PHP `max_input_vars` above `3 × largest district roster + 20` (for example 5,000). Incomplete forms are rejected rather than silently interpreted as a completed review.

## Verification and pilot acceptance

Run `python3 verification/verify.py` for PHP syntax checks, XMLDB structural checks and executable workflow/AD adapter contracts. These tests use in-memory Moodle data and simulated LDAP functions; they do not contact a real Moodle instance or AD server.

Before production use, test on Moodle 5.1.1 with dedicated AD test accounts:

1. Complete installation and open settings, dashboard, management, review and approval pages.
2. Check two assigned reviewers can share a district roster; a stale save is rejected. An unrelated logged-in user and a logged-out visitor cannot retrieve its roster or submit changes, including by changing IDs.
3. Check one unchanged user, one departure and one transfer. Confirm the default status, destination dropdown, signed-in submitter, admin email, selections/exclusions, and preview mode.
4. Preview current AD state, process only the departure, and inspect ECBOCES_Members, Zoom, Basic, Office and unchanged Company directly in AD.
5. Process the transfer and inspect retained ECBOCES_Members, removed Zoom, added Basic, Office `No Access` and exact new Company.
6. Run your existing sync and confirm Moodle Institution reflects Company. Confirm any Zoom license/group provisioning behaves as intended.
7. Deny one delegated permission deliberately on a test account, verify partial results/audit, then repair permissions and retry. Test a nested group case is blocked.
8. Verify invitations/reminders with test recipients, then turn on your chosen annual schedule.

**Current verification boundary:** PHP lint, schema structure and 81 offline contracts pass. The plugin passed Moodle’s own ZIP validation and XMLDB parser, and version 0.1.9 deployed and completed its version update on the local Moodle 5.1.1+ test site (Build: 20260205; core version 2025100601.11). All six plugin tables were verified, the management page rendered in a CLI request, and AD writes and automatic annual reviews remained disabled. The roster-refresh integration check also passed against the real Moodle database: adding users, preserving responses, freezing submitted reviews, reopening, removing inactive untouched entries and repeated refresh were verified inside a transaction, then all fixture data was rolled back. The real-database custom-profile check verified District-only matching with blank Institution and an unknown email domain, and rematching after the profile value changes; all temporary field definitions, values and user records were rolled back. The real-database retention check also verified the exact 30-day cutoff and that manual assignments survive deletion of their audit records. Run `php verification/moodle_refresh.php /path/to/moodle/config.php --test-site` only against a test site to repeat it. The 0.1.8 real-Moodle security check passed: recent reviewer access, expired direct access, dashboard hiding, administrator access, reopening and the link-only admin email received in local Mailpit were verified, with database fixtures rolled back. Full browser reviewer workflows, LDAP authorization, mail delivery beyond the local catcher and downstream sync still require the pilot checks above. This is a pilot package, not a production validation claim.
